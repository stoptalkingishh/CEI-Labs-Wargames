# Build plan: Maze (2026-07-24)

Level-by-level content plan for a future CEI Labs Maze track. This
game has the best source coverage of the four binary-exploitation
tracks in this planning series (only Leviathan's is comparably solid).
Structured to match the conventions already established by
Bandit/Krypton/Natas in `CEI-Labs-Wargames`. Planning doc only -- no
code, targets, or challenge definitions created in this pass.

## Sources

- `l3ouu4n9.github.io`'s Maze wargame post (fetched directly, covers
  all levels 0-9)
- Upstream: `overthewire.org/wargames/maze` confirms 9 levels
  (maze0-maze8), difficulty 5/10, "Can you find the way out?" framing,
  passwords stored at `/etc/maze_pass/maze<N>`. No per-level text
  published there. (Note: upstream says 9 levels, maze0-maze8; the
  fetched walkthrough's numbering runs through "maze9" as a completion
  marker with no separate technical content -- treated below as 9 real
  levels plus a completion step, consistent with upstream's count.)

## Level-by-level plan (9 levels, maze0 -> maze8, per upstream's own count)

| Level | Technique (per source) | CEI Labs equivalent notes |
|---|---|---|
| 0->1 | Race condition exploiting symlink (TOCTOU-style) behavior to read a restricted file | New category for CEI Labs -- no existing track has a race-condition level; would need an original tier-1 hint explaining TOCTOU from scratch |
| 1->2 | Function hooking via a custom shared library intercepting `puts()` | New category -- `LD_PRELOAD`-style hooking has no precedent in this repo |
| 2->3 | Buffer overflow with shellcode placed in an environment variable plus an assembly jump | Same technique family as the Utumno plan's level 3 (EGG-variable shellcode) -- strong candidate to share/reuse hint design between the two tracks if both get built |
| 3->4 | Reverse-engineered XOR decryption of dynamically self-modifying machine code | Advanced reverse-engineering level; no precedent elsewhere in this repo |
| 4->5 | ELF header manipulation to bypass a file-validation check | Conceptually adjacent to Natas-13's "bypass a content-based file-type check" (there, `exif_imagetype()`; here, raw ELF header bytes) -- could reuse some of that level's hint-design lessons despite being a completely different runtime environment |
| 5->6 | Reverse-engineering an authentication function to derive valid credentials directly (rather than exploiting memory corruption) | Closer in spirit to Krypton's cipher-breaking levels than to a memory-corruption level -- worth flagging as a change of pace within the track |
| 6->7 | Format string vulnerability -- the walkthrough author explicitly called this level "too hard" and didn't fully solve/document it | First format-string level referenced in this planning series; flagged as a genuinely hard one even for an experienced write-up author, so hint design here needs real care, not a quick adaptation |
| 7->8 | Stack buffer overflow via a crafted ELF file controlling the instruction pointer | Same overflow family as several other tracks' levels, but delivered via a crafted file rather than direct input |
| 8-> (final) | Format string vulnerability over a network socket, modifying GOT entries | Most advanced level in the track; combines the format-string category from level 6->7 with a network-service delivery mechanism, similar in spirit to Bandit's netcat/openssl levels but with a much harder payload |

## Structural fit against existing conventions

Same shape as the other four plans: `targets/maze/` mirroring
`targets/bandit/`'s layout, a distinct banner palette/art following
the "labyrinth/non-linear path" lore in
`docs/future-wargame-theme-maze-2026-07-24.md` (already noted there as
thematically distinct from the other three binary-exploitation tracks'
"descending depth" lineage), and `scripts/build_maze.py` with the same
`TITLES`/`EXTRA_INFO`/`HINTS`/`_render_description()` shape.

`docs/future-wargame-theme-maze-2026-07-24.md` already flagged a
question about whether CEI Labs' per-team relaunch model fits a "one
wrong step breaks everything" design. This level list reinforces that
question is real and specific, not hypothetical: several levels here
(2->3, 6->7, 7->8, 8-final) involve crafted shellcode/payload delivery
where a bad attempt could plausibly leave the target process in a bad
state -- confirming whether "relaunch to reset" is the intended
recovery path needs to happen before implementation.

## What this needs before it's an actual implementation plan

- This is the strongest-sourced plan of the five, but it is still a
  single secondary source, not independently cross-verified the way
  the Bandit/Krypton/Natas hint cross-references checked against our
  own existing `HINTS` dict. Before writing real challenge content,
  the actual upstream Maze levels should be reproduced/verified
  directly rather than trusting one blog's account of each level,
  especially for the two levels the source author flagged as
  difficult or partially unsolved (6->7, and implicitly 8).
- Highest technical difficulty of the five tracks in this series
  (upstream's own 5/10 rating is the highest among the five) --
  format-string-over-a-network-socket and self-modifying-code levels
  in particular would need real subject-matter review before CEI Labs
  commits to building them as-is.
- Same memory-corruption containment review needed as Narnia/Behemoth/
  Utumno, plus a network-facing-service-specific review for level
  8->final given it involves a listening socket rather than a local
  binary.
