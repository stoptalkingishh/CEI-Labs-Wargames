# Sentinel Lab Design Matrix

## Purpose

This matrix turns the Sentinel curriculum plan into reviewable lab contracts.
It describes the proposed mechanism and validation for each lab; a `Planned`
row is not an implementation claim. All labs use the per-team Sentinel SSH
target unless the row explicitly says static artifact. No lab uses public
targets, live malware, production evidence, unrestricted network access, or
generic privilege escalation.

`Built` refers to [PR #68](https://github.com/stoptalkingishh/CEI-Labs-Wargames/pull/68),
which remains non-staged pending platform integration.

| 01 Asset Census | Built | 4.1, 4.2: reconcile an inventory with real host state. | Compare a supplied CMDB-style record with installed packages, active services, ports, and ownership data. | Dynamic flag is in the correctly identified asset record; expected command/output fixture test. | Core Linux tools: `dpkg`, `systemctl`, `ss`, `stat`; synthetic inventory. | Build-time fixtures; runtime secret renders the next credential only in the intended evidence. |
| 02 Control Review | Built | 1.1, 1.2: classify controls and relate them to CIA/AAA. | Inspect control cards and host evidence to identify the required category and control type. | Flag follows the only evidence-supported classification; content test rejects ambiguous alternatives. | Static control cards and local host configuration excerpts. | Versioned text artifacts under the target; generator description and hints use original scenarios. |
| 03 Change Window | Built | 1.3: recognize security-relevant change-management gaps. | Review a change ticket, approval trail, test result, dependency note, and rollback plan. | Flag is associated with the missing required control; artifact contract checks required/absent fields. | Static change-management records and a local Git-style diff. | Build-time records, fixed timestamps, and no service mutation needed. |
| 04 Certificate Trail | Built | 1.4: assess certificate trust and key handling. | Inspect a supplied certificate chain, private-key permissions, and local revocation evidence. | Dynamic flag follows the trustworthy service identity; OpenSSL/permission test confirms the intended result. | OpenSSL; generated test CA, certificates, CRL/OCSP-like fixture. | Build test PKI fixtures; entrypoint derives only the next credential, never a production-style secret. |
| 05 Attack Surface | Built | 2.2, 2.5: identify exposed service risk and hardening action. | Enumerate listeners and service configuration, then identify an unintended default service. | Dynamic flag is in the intended configuration evidence; wrong-user access and SSH-only exposure tests pass. | `ss`, `systemctl`, OpenSSH; static service configuration. | Keep only SSH live; represent additional services as evidence/configuration, not exposed daemons. |
| 06 Suspicious Access | Planned, batch 1 | 2.4, 4.4, 4.9: identify a password-spray chain, scope it, and name the monitoring implication. | Correlate a deterministic, UTC-only corpus at `/var/lib/sentinel/lab06/raw/auth.log` with a local `last` fixture and benign noise. A provenance manifest records synthetic source, generator revision, corpus checksum, and ground-truth timeline; learners use the raw-log path, not `journalctl` or `ausearch`. | Structured answer requires `account`, `source`, `window_start_utc`, `window_end_utc`, and `monitoring_implication`. The validator accepts only the ground-truth tuple and rationale; timeline, provenance/checksum, raw-path, and wrong-user-denial tests pass. | `last`, `grep`, `awk`; synthetic auth log, `last` fixture, and provenance manifest. | Generate the fixed UTC corpus and manifest at build time. Derive only the final credential at startup; keep the corpus journal-independent and omit `ausearch` initially. |
| 07 Vulnerability Triage | Planned, batch 1 | 2.3, 4.3: classify a vulnerability, confirm affected status, and choose a context-aware remediation priority. | Compare a mock scanner finding and CVE advisory with installed package epoch/version/release, distribution backport statement, compensating control, exploitability, and asset criticality. The advisory states whether its fixed version is upstream or distribution-packaged so learners must apply backport semantics rather than raw version ordering. | Structured response requires `vulnerability_type`, `affected_status`, `priority`, `response`, and `validation`. A deterministic rubric assigns priority from affected status, exposure/exploitability, asset criticality, and control effectiveness; fixtures assert one classification, finding state, score, response, and validation result. | Static advisory, scan output, package inventory, backport note, compensating-control evidence, and risk worksheet. | No live scanner or feed. Store versioned fixtures and rubric inputs; make epoch/version/release comparison and backport disposition explicit in the worksheet. |
| 08 Least Privilege | Planned, batch 1 | 2.5, 4.6: audit effective access, identify an over-broad delegation, and specify the least-privilege correction. | Analysis-only: inspect one read-only evidence package containing users, groups, ACL entries, role definitions, and an effective-access table that resolves group and ACL inheritance for the target resource. The sole learner path is `/var/lib/sentinel/lab08/evidence/`; no account, ACL, or `sudoers` mutation is available. | Structured assessment requires `principal`, `resource`, `effective_access`, `role_mismatch`, and `recommended_state`. The validator accepts only the evidence-supported finding and correction state; tests prove the table resolves the intended access, the evidence path is readable by the learner, and neighboring accounts cannot read the credential. | `id`, `getfacl`, `stat`; read-only controlled account/group/ACL snapshots, role definitions, and effective-access table. | Build a static, checksumed evidence package with non-world-traversable credential storage. Permit no `sudo`, root shell, correction helper, cross-account access, or writable ACL/account state; reset is a deterministic artifact rebuild. |
| 09 Segmented Services | Planned, batch 2 | 3.1, 3.2: choose a safe management path through zones. | Interpret a named four-zone architecture: user, management/bastion, application, and data. Reconcile its documented flows with an ordered, first-match static ruleset to identify an unsafe direct flow and the approved management-mediated path. | Structured answer requires `source_zone`, `destination_zone`, `protocol_port`, decisive `rule_id`, and ordered `safer_path` zone/rule IDs. Fixture tests require every documented flow to resolve under first-match/default-deny semantics and reject alternate paths or rule-order interpretations. | Static architecture/zone diagram, flow table, and ordered `nftables`-style ruleset with rule ID, sequence, source/destination zone, protocol/port, and action. | Static only: no live firewall, namespace, or `CAP_NET_ADMIN`. Use fictional, fixed artifacts whose zone names and flow IDs agree across the diagram, flow table, and ruleset. |
| 10 Data Handling | Planned, batch 2 | 3.3: classify data and select protection by state. | Review synthetic policy records bound to a versioned policy contract. Each record supplies its ID, data type, classification, geography, state, and use case; the policy's scoped control table identifies the permitted and required control for that combination. | Structured per-record answer requires `record_id`, `policy_id`, `policy_revision`, `data_state`, `selected_control`, and `rationale_rule_id`. Content tests cover every record, confirm that the cited version and rule scope apply, and reject controls that are valid only for another type, state, geography, or use case. | Static policy contract with policy ID, revision, effective date, definitions, and scoped control table; synthetic data records; local answer worksheet. | Offline and static-first: no real PII and no OpenSSL verification. OpenSSL is explicitly deferred unless a later review establishes a bounded, objective-specific need. |
| 11 Recovery Evidence | Planned, batch 2 | 3.4, 5.2: validate backup/recovery readiness and RTO/RPO. | Reconcile a BIA, backup manifest, retention record, and recovery-drill log using one workload ID and fixed UTC reference time. A recovery succeeds only when the restored checksum matches the manifest checksum and the measured drill duration is within the BIA RTO; the recovery point is the manifest snapshot time and must be within the BIA RPO at the reference time. | Structured readiness answer requires `workload_id`, `bia_id`, `rto`, `rpo`, `recovery_point_utc`, `recovery_point_age`, `recovery_duration`, `checksum_result`, `readiness`, and cited evidence IDs. Fixture tests reconcile identifiers, timestamps, retention, checksum values, RPO age, and RTO duration, and reject an otherwise successful restore that misses either time objective. | Static BIA, backup manifest, retention record, recovery drill log, and checksum manifest for synthetic data. | Offline and static-first: no restic repository or restore command. Restic is explicitly deferred unless a later review requires a deterministic local synthetic-data restore test. |
| 12 Baseline Drift | Planned, batch 3 | 4.1, 4.7: detect and safely remediate baseline drift. | Compare a provenance-manifested approved baseline with current service/configuration evidence, explain the drift and guardrail context, then use the restricted helper only after submitting a structured diagnosis. | The assessment requires the affected control, evidence-supported drift, approved remediation, and expected post-state before the helper is available. Post-change verification matches the identified baseline; tests prove the helper is command/path-restricted, idempotent, resettable, and denies arbitrary commands or state changes. | Core Linux tools; optional Lynis/osquery report; versioned baseline/current evidence and provenance manifest; restricted shell helper. | Build fictional approved/current fixtures with revision, fixed UTC timestamp, source/context, and checksums as applicable. Use a fixed-command helper owned by an admin group, not broad `sudo`; reset restores the pre-remediation fixture state. |
| 13 Integrity Alert | Planned, batch 3 | 1.4, 4.4, 4.5: investigate a file-integrity alert. | Use a provenance-manifested, timestamped evidence set in this order: verify the hash-manifest identity and timestamp, compare the protected-file hash, confirm package ownership, then reconcile the authorized change record to classify the modification. | The assessment requires the affected asset, observed versus approved hash result, modification classification, and proportionate response/containment decision before the credential is released. Tests use deterministic hash/owner/change-record fixtures, pin manifest and evidence timestamps, and reject internally inconsistent provenance. | `sha256sum`, `dpkg -S`; optional AIDE-style report; versioned hash manifest, ownership fixture, and change record. | Build synthetic protected files and signed/hashed manifests with fictional source, revision, fixed UTC hash-generation timestamp, evidence-collection timestamp, and consistent identifiers; no real malicious file. |
| 14 Identity Lifecycle | Planned, batch 3 | 4.6: verify secure offboarding. | Reconcile a closed offboarding ticket, identity inventory snapshot, revoked-key register, and deprovisioning attestation for a fictional former worker. The target contains no corresponding account, credential, or authorized key. | Structured conclusion identifies the missing offboarding record and its required follow-up; fixture tests prove the former identity cannot resolve locally and no usable key or credential exists. | Static identity inventory, ticket, revoked-key register, group snapshot, and attestation; `getent` only to confirm absence. | Inert evidence-only model with tombstoned identifiers and non-functional key fingerprints. No mutation helper, target account, password, private key, or authorized-key material is created. |
| 15 Alert Tuning | Planned, batch 3 | 4.4: distinguish true alert from false positive and document tuning. | Run one documented, locale- and UTC-independent `jq` query against the supplied immutable JSON corpus, then classify the scoped alert and propose a bounded tuning rule. The corpus manifest records fictional organization, revision, fixed UTC timestamps, event IDs, and checksum; deterministic benign-noise events remain attributable to their source and are distinguishable only through evidence. | The structured response must identify evidence event IDs, classification, proposed tuning, expected false-positive reduction, and the tradeoff/coverage retained. The fixture test runs the documented query, checks a single scoped result and response schema, and proves the tuning suppresses only the known noise while retaining the true-positive event. | `jq`, `grep`, JSON event corpus; Suricata EVE JSON may be added after offline PCAP work. | Versioned JSON logs and provenance manifest with checksum; ground-truth labels and instructor timeline are withheld from learners. Publish the exact query path and expected fields, not a hidden-string retrieval path. |
| 16 Secure Service Change | Planned, batch 3 | 4.5, 4.7: apply a reversible security change through automation. | Review approved change evidence, including scope, authorization, test, and backout plan, before invoking a restricted idempotent helper. The helper performs one approved mutation only after the learner records the precondition, intended mutation, expected postcondition, and backout assessment. | Automated test verifies review precedes helper access, the structured assessment schema, precondition, exact allowed mutation, postcondition, backout, idempotence, reset, action log, and no shell escape or unauthorized state change. | Shell/Python helper, static service configuration; optional `nft` only in a private network namespace. | No generic configuration write access. The exercise uses static configuration unless an isolated private namespace is required; it never changes host firewall or service state. Helper accepts no arbitrary paths/commands, writes an append-only action log, and reset restores the documented initial state. |
| 17 Incident Containment | Planned, batch 4 | 2.4, 4.8, 4.9: build a timeline, scope incident, choose preservation-safe containment. | Correlate raw auth, process, application, firewall, and PCAP evidence from one controlled incident. Every record carries fixed UTC time, source host, event/source identifier, and incident correlation field; the provenance manifest records artifact revision and checksums for PCAP or other binary evidence. | A structured response must supply ordered timeline events, affected host/account/source scope, and one containment action with its preservation rationale. A unique rubric accepts only the evidence-supported action and rejects broader, destructive, or unsupported containment. Tests assert correlation, ordering, scope, rubric uniqueness, and an unchanged evidence corpus. | `grep`, `jq`, `tcpdump -r`; optional offline Suricata EVE JSON. | Create one timestamped synthetic incident corpus with benign distractors and a documented instructor timeline kept from learners. Provide three lab-specific hints: locate the correlated records, interpret the scope, then validate the preservation-safe action; feedback identifies the missing timeline, scope, or containment field without exposing the answer. |
| 18 Forensic Handoff | Planned, batch 4 | 4.8: preserve and document evidence. | Work a fictional case with an identified receiving custodian. Verify the provenance manifest and its signature decision, then prepare a chain-of-custody handoff without altering source evidence. | A structured handoff must identify case and evidence IDs, recipient, hash/manifest result, signature-verification decision, transfer time, and custody statement. Tests validate the completed handoff, reject malformed or failed-verification decisions, prove raw-evidence hashes remain unchanged, and cover restart plus validation-error handling. | `sha256sum`, `stat`, signed/hash manifest, chain-of-custody form. | Publish source evidence through a read-only evidence filesystem and provide a separate writable workspace for the handoff; the contract denies writes to raw evidence. Use fictional data, fixed provenance fields, and lab-specific hints to locate the case context, assess manifest/signature evidence, and complete the handoff; field-level feedback names missing or inconsistent handoff data without disclosing values. |
| 19 Policy to Practice | Planned, batch 5 | 5.1: distinguish governance documents and accountable roles. | Match host evidence to policy, standard, procedure, owner/controller/processor/custodian responsibilities, then submit the governance gap, accountable role, and that role's responsibility. | Flag follows a structured governance answer; content test requires the gap, role, and responsibility fields and prevents multiple evidence-supported matches. | Static policy/standard/procedure/RACI and host evidence package; versioned artifact manifest with per-artifact revision and SHA-256 checksum. | Original fictional documents with stable version/revision metadata; publish a versioned manifest so learners can verify the supplied artifact set before assessment. |
| 20 Risk Register | Planned, batch 5 | 5.2: calculate and prioritize risk, then select treatment. | Use a small risk register/BIA with named source fields, declared currency/time units, and stated rounding to calculate SLE, ARO, and ALE; compare RTO/RPO and risk appetite, then select from treatment options constrained by the supplied control and business context. | Flag follows a structured risk decision containing source values, intermediate SLE/ARO/ALE calculations, priority, treatment, business consequence, and accountable owner; tests validate field sources, units, rounding, formulas, treatment constraints, and a unique evidence-supported decision. | Static CSV/JSON risk register, BIA, calculation worksheet, and input manifest defining source fields, units, and rounding; shell/Python arithmetic only. | Fixed fictional values with transparent formulas and bounded treatment choices; identify the business consequence and owner for each decision, with no external GRC tool. |
| 21 Assurance Review | Planned, batch 5 | 5.3-5.6: make a vendor-assurance renewal decision. | Review one vendor's due-diligence questionnaire, agreement and service commitments, compliance/attestation evidence, audit finding, and remediation response. | Structured assessment requires an evidence citation and decision for each retained 5.3-5.6 criterion, then derives one approve-with-conditions, escalate, or decline renewal decision. Content tests require one internally consistent decision and reject incomplete or cross-vendor answers. | Static, revisioned vendor questionnaire, agreement/SLA excerpts, compliance attestation, audit finding, remediation response, and decision form. | One fictional vendor and fixed UTC document revisions; no phishing scenario, live email, reputation lookup, external service, or additional challenge. |

## Cross-lab validation requirements

The design details for the shared validator, fixture manifest, hints/debriefs,
mutation helpers, and PR #68 gate are in
[`sentinel-ooda/shared-remediation-contracts.md`](sentinel-ooda/shared-remediation-contracts.md).
They are implementation contracts, not evidence that a target or runtime check
has been completed.

- Every scored challenge has a unique per-team dynamic flag, three progressive
  managed hints, an instructor writeup, and a YAML/content invariant test.
- Dynamic-secret labs prove fail-closed startup, deterministic restart output,
  secret scrubbing before SSH starts, and cross-account denial.
- Artifact-only labs use stable timestamps, fictional data, checksums for
  binary evidence, and a test that confirms one intended answer.
- Any mutation helper is command- and path-restricted, idempotent, reversible,
  logged, and tested for shell escape and unauthorized state changes.
- Offline evidence tools use pinned versions, local artifacts, and no network
  feeds, live capture, or external DNS.
